# Titan — Decisions Log

Dated record of real decisions and the reasoning behind them, so nothing gets accidentally re-litigated by a future session. Append new decisions at the bottom; never delete a past one — if it's reversed, add a new entry that supersedes it and say so.

## Pre-repo decisions (from initial scoping conversation)

1. **Don't build the full original vision.** Build the smallest slice that would actually get used daily.
2. **New, separate app** from Budget Tracker — clean slate, reusing the same proven stack.
3. **Reuse the Capacitor + Ionic + React pipeline** rather than starting over with native Kotlin/Jetpack Compose.
4. **Skip AI auto-routing.** User manually picks which AI answers each chat. Simpler, works immediately, and teaches what "smart routing" should look like before automating it.
5. **All 3 AI providers (Claude, GPT, Gemini) from day one**, made viable by the shared "plug" pattern and BYOK (no reselling/ToS problem, no cost to Ashish).
6. **Architecture must stay extensible** — future providers are a new plug, not a redesign.
7. **Skip OAuth / Gmail / Calendar / Drive for v0.1.** Manual only, initially.
8. **Skip vector database for v0.1.** Simple per-project notes files instead — mirrors how short saved summaries (not raw transcript replay) already work well at small scale.
9. **No backend server for v0.1.** App calls each AI's API directly from the client.
10. **Token/context limits are not a v0.1 concern.** Current model context windows comfortably exceed a project's notes + a few files. Long-term design principle: save short summaries, retrieve only what's relevant — not "a bigger limit."

## 2026-08-15 — Repo setup and build-order refinement

11. **Build order: Chat screen before Settings screen**, reversing the original spec's literal order. Reason: proving the riskiest unknown (does a direct client-to-AI-API call actually work end-to-end on-device) should happen before building screens on top of it.

12. **CORS risk handled via Capacitor's native HTTP plugin, not a backend.** Anthropic's API (and likely OpenAI/Google's) doesn't set CORS headers for browser-origin requests, so a plain WebView `fetch()` may fail. Routing the request through `CapacitorHttp` (native code, not the browser sandbox) avoids the restriction without adding server infrastructure — keeps decision #9 intact in practice, not just in letter. To be validated by an explicit spike as the first build step.

13. **API keys stored via Capacitor Preferences plugin**, not a Keychain-backed Secure Storage plugin. Threat model for a single-user sideloaded app is "someone else picks up my phone," not "attacker with device root" — the extra setup of secure storage isn't justified yet.

14. **Notes generated by naive truncation, not an AI-generated summary.** Free, instant, zero extra API calls. Ship this first; only add a summarization call later if the trial period shows it's genuinely insufficient.

15. **AI picker default persists per project**, not reset per message.

16. **Missing/invalid API key UX:** disable send, show inline prompt to add the key in Settings. No proactive key validation (no test call per keystroke) — just surface the provider's real error when it happens.

17. **File attachment deferred to v0.2**, bundled with Drive integration rather than reopened standalone in v0.1.

18. **Google Drive integration is real, scoped, and deliberately pushed to v0.2** — not folded into v0.1, and not dropped either. Confirmed scope: project notes + chat history sync, plus Drive-backed file storage/attachments, mirroring Budget Tracker's existing pattern. Reopens OAuth (previously deferred by decision #7) once the core app is proven, not before.

19. **"The app should train itself" reframed as memory/personalization, not model training.** Neither Anthropic nor (practically) OpenAI/Google support fine-tuning in a way that fits a personal BYOK client app — no fine-tuning API for Claude at all, and OpenAI's fine-tuning is heavyweight, per-provider, and breaks the plug pattern. What's actually achievable and matches the intent — "it remembers me, it gets smarter about me" — is context injection via the notes system (decisions #8, #10, #14), which is already in scope. No new roadmap item was needed; this decision exists to prevent a future session from trying to literally build model fine-tuning.

20. **OTA update mechanism moved from "once stable" into v0.1**, in a lightweight self-rolled form (public JSON manifest + `www`-folder swap), rather than waiting for v0.2's Drive integration or adopting a paid service (Capgo/Appflow). Motivated by real friction: manual rebuild-sideload-reinstall on every change plus Android's Play Protect warnings on sideloaded APKs. Consistent signing across builds (so installs are treated as upgrades, not new "unknown" apps) resolves most of the Play Protect friction as a one-time cost. Once Drive lands in v0.2, the manifest moves to the user's own Drive folder, dropping the third-party OTA service question entirely.

21. **Device-wide / cross-app control explicitly excluded from Titan**, not deferred to "someday." Requested during this conversation ("take control of my phone over all apps... personal assistant"), then withdrawn by the user ("let it be") after review of the original handoff doc confirmed this wasn't even part of the original vision. Reasoning it was rejected on, kept for the record: Android has no API for one app to control another generally; the closest real capability (Accessibility Service automation) is a different engineering domain from a chat app, carries a large security surface (effectively a master key to the device), and repeats the exact over-scoping pattern the original vision assessment already flagged and cut once. If ever pursued, treat it as a wholly separate project with its own scoping discussion — not a Titan phase.

22. **Git workflow: `main` / `develop` / `feature/*` (and `bugfix/*`)**, per the original handoff doc's explicit preference (item 27). `main` and `develop` established as the repo's backbone at the same time as this documentation set; feature work (including this documentation itself) goes through a branch and a PR into `develop`, not direct commits to `main`.

23. **Seven-document handoff structure established** (`PROJECT_CONTEXT.md`, `ARCHITECTURE.md`, `ROADMAP.md`, `DECISIONS.md`, `CHANGELOG.md`, `ERROR_LOG.md`, `AI_HANDOFF.md`, plus `docs/source/` for the two original vision documents verbatim), per the original handoff doc's explicit requirement (item 28) that Titan stay transferable across GPT/Claude/Gemini sessions.

## 2026-08-15 — v0.1 build

24. **In-app OTA (decision #20) reversed: not shipped in v0.1.** Attempted the "lightweight self-rolled" version and found no version of it was actually lightweight once evaluated properly. The realistic options were: (a) `@capgo/capacitor-updater`, whose default config phones home to Capgo's own servers for stats/channels/update-checks unless every one of several config flags is set correctly to disable it — a real conflict with Titan's no-third-party, BYOK-only posture, on top of a plugin API surface (channels, delta updates, encryption, preview sessions) far beyond what a single-user app swapping a small React bundle needs; or (b) hand-written native code to override which folder Capacitor's WebView serves from, which risks bricking the app on a bad update with no way for this session to test it on a real device first. Both risks are avoidable, and the friction OTA was meant to solve is already substantially addressed by the CI pipeline (decision below) plus consistent debug signing — a new build is one tap to install, not a full rebuild. True in-app OTA is deferred to v0.2 alongside Drive, where the update payload can be self-hosted in the user's own Drive folder instead of depending on either option above, and where on-device testing will actually be possible before it ships.

25. **CI (GitHub Actions) builds and publishes a debug APK on every push/PR**, since this build environment has no Android SDK and cannot produce an APK itself. This is the actual mechanism decision #20 was reaching for: it replaces "rebuild and sideload locally" with "download the latest workflow artifact and tap install," without the risk carried by decision #24's rejected options.

26. **Debug builds signed with a checked-in, fixed keystore** (`android/app/debug.keystore`, no meaningful access — debug-only), rather than letting Android auto-generate one. CI runners are ephemeral, so without this every CI-built APK would carry a different signing key, and Android refuses to install an APK over a previous install if the signature doesn't match — forcing an uninstall (and wiping on-device Preferences data: projects, chat history, notes) on every single test cycle. This was caught before it could bite, not after.

27. **All three providers built together in v0.1's first pass, not incrementally.** Decision #5 already committed to all three from day one; once the plug interface existed, implementing Claude/GPT/Gemini together cost little more than implementing one, so the roadmap's originally-staged "Claude first, then add GPT/Gemini" ordering was collapsed into a single pass.

28. **Settings screen built alongside Chat, not after it**, superseding the roadmap's originally-planned "hardcoded key" milestone. The hardcoded-key step assumed someone would edit source code to drop in a key for early testing; given the owner's actual workflow ("I will only keep testing the app and make conversations" — no source editing), the key has to come from a real on-device UI from the very first testable build, so Settings was pulled forward rather than sequenced after Chat.
